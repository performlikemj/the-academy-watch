**M1 — backend money safety**

1. **Execution creation must be atomic with reservation.** `src/services/gol_credits.py:98`, `:106`, `:158` already provide the user lock and commit boundary. “Or immediately after” permits another request to observe the debit without its execution and start a second model call. Sequential replay tests pass despite this race. **Replace:** “Create or claim the execution inside `reserve_question`, under the existing user lock, and commit debit plus execution together; never create the execution in a subsequent transaction. Test overlapping requests using independent PostgreSQL transactions.”

2. **Stale recovery contradicts the proposed unique key and lacks worker fencing.** The debit’s `attempt` is fixed by `src/services/gol_credits.py:115`; marking an execution failed does not release `UNIQUE(user_account_id, client_msg_id, attempt)`. Incrementing only the execution attempt disconnects it from reservation lookup. A five-minute-old worker can also still be alive. The single stale-row test misses both problems. **Replace:** “Keep one execution per debit attempt and reclaim it atomically using a separate lease generation; completion and compensation must verify that generation. Specify the recovery limit, and test two simultaneous reclaimers plus an old worker returning after takeover.”

3. **Exact-attempt compensation needs an explicit caller contract.** `src/routes/gol.py:105` refuses compensation when `debited=False`, which includes the proposed recovered execution. `refund_question(user, client_msg_id)` at `src/services/gol_credits.py:167` has no reservation from which to infer an attempt. A sequential error→retry test cannot catch an old callback refunding attempt 2. **Replace:** “Return the debit ID and execution ownership from reservation; every streaming compensation passes that exact debit ID, including recovery without a new debit. Retain latest-debit behavior only for legacy callers, and test a delayed attempt-1 error after attempt 2 starts.”

4. **“On stream completion” is too ambiguous for durable replay.** `src/services/gol_service.py:464` yields an error and then returns normally; `:604` yields `done`. `src/routes/gol.py:130` treats disconnect separately. An implementation can therefore mark failed output completed, or deliver `done` before saving the answer and rerun after a crash. **Add:** “Persist successful output before forwarding the terminal `done`; an error event, exception, or EOF without successful completion must never mark the execution completed. Define disconnect handling explicitly and test error-then-normal-return, token-only EOF, and failure between persistence and delivery.”

5. **The proposed hash still omits effective model input.** `src/services/gol_service.py:624` preserves `tool_calls` and `tool_call_id`; `src/hooks/useGolChat.js:9` sends those fields through hidden history. Hashing only role/content lets callers change tool arguments under the same ID. The proposed history-content-change test passes while that hole remains. **Replace:** “Hash the complete validated history accepted by `_sanitize_history_entry`, including assistant `tool_calls` and tool `tool_call_id`, together with message and session ID; define normalization consistently with the actual model input and reject malformed input before reserving. Test tool-field-only and session-only changes.”

6. **Text-only replay is not replay of the existing answer contract.** `src/services/gol_service.py:597` emits `history_entries`; `src/hooks/useGolChat.js:208` and `:224` retain cards and hidden context. M1 stores meta but never explicitly replays it. Also, `src/routes/gol.py:65` initializes `GolService` before looking up replay, making a saved answer unavailable during initialization failure. **Replace:** “Replay `usage`, `replace` with `{content: response_text}`, ordered `data_card` and `history_entries` events, then `done`; resolve completed/in-flight executions before constructing `GolService`. Test a tool-using answer and replay while service initialization fails.”

7. **The refund hold still has a lost-refund race.** At `src/services/stripe_billing.py:793`, refund can observe no grant; meanwhile checkout can grant and inspect no hold at `:717`; refund then commits its hold. Both handlers succeed, leaving credits unreversed. The user lock does not protect the unmatched-refund branch. **Replace:** “Serialize both handlers on the same durable payment-intent state before either decides whether a grant or hold exists, with a consistent lock order and atomic reconciliation. Test this exact interleaving with two PostgreSQL connections; back-to-back calls are not concurrency evidence.”

8. **Hold updates must be monotonic and remain reconcilable after first application.** `src/services/gol_credits.py:268` already computes cumulative refund targets and `:293` retains the maximum. A naïve hold upsert lets a delayed partial refund overwrite a full refund; an `applied_at` shortcut can suppress subsequent increases. Ascending partial→full tests miss this. The held path also bypasses the refund analytics at `src/services/stripe_billing.py:804`. **Add:** “Store the maximum cumulative refunded amount, including concurrent upserts; reconcile every increase even after a hold was previously applied, and emit `gol_credits_refunded` only for newly reversed credits. Test full→partial→grant, repeated amounts under different event IDs, and a larger refund after application.”

9. **A checkout row is currently mutable across Stripe sessions.** `src/services/stripe_billing.py:232` resets the row and `:262` replaces its session ID; `_checkout_row` at `:601` falls back to the reused local row ID. A delayed event for the old session can therefore consume the new session’s snapshot. The proposed config-change tests use only one session. **Replace:** “Bind each snapshot immutably to its exact Stripe session; do not overwrite a prior session’s purchase terms when reusing a client key, and never fulfill an old event from a different session’s snapshot through `client_reference_id`. Test expiration/recreation followed by delayed completion of the original session.”

10. **Snapshotting only an uncommitted checkout row does not survive process death.** Stripe creation occurs at `src/services/stripe_billing.py:251`, before the caller commits the local transaction. A remote session can exist after local rollback; retry after configuration changes can receive the idempotent old session while recording new credits. A webhook arriving before local commit also appears orphaned. **Add:** “Persist the purchase intent and its immutable terms before the external Checkout creation call, then attach the returned session idempotently; recover a crash after remote creation without resnapshotting from current configuration. Exercise this with fakes and transaction rollback.”

11. **Deletion will fail unless execution rows are removed explicitly.** `src/services/account.py:621` rejects unclassified account FKs before deleting the user, so `ON DELETE CASCADE` alone cannot satisfy the deletion policy. `src/services/gol_credits.py:332` deletes ledger rows before the new debit/grant references are handled. Export at `src/services/account.py:323` also omits stored answers, but the file fence permits deletion changes only. **Replace:** “Permit account export changes as well as deletion changes; export owned executions, explicitly delete them before ledger forfeiture, and define cleanup or `SET NULL` behavior for hold-to-grant references. Test real account deletion with completed/running executions and an applied hold under PostgreSQL or FK-enforced SQLite.”

12. **Missing checkout does not prove a deleted account or a refundable payment.** `_apply_gol_checkout` checks missing ownership before paid status at `src/services/stripe_billing.py:691`; routing at `:741` accepts every payment-mode session, and `:757` separately handles async success. Missing rows can also mean the creation race above. Distinct completed/async events can produce duplicate manual-refund records for one purchase; event-ID deduplication at `:887` does not prevent that. **Replace:** “Classify orphan settlement only for an identified Academy Watch GOL purchase with successful payment evidence; distinguish deletion from recoverable missing purchase state, deduplicate manual-refund work by purchase identity, and cover unpaid completion, async success, unrelated payment sessions, and both deletion/webhook lock orders.”

13. **The proposed migration-generation command is not supported by these guards.** `migrations/_migration_helpers.py:11`, `:20`, `:29` execute catalog queries and call `.scalar()`, which offline `--sql` execution cannot satisfy. SQLite `create_all()` tests at `tests/test_gol_credits.py:83` prove neither migration guards nor RLS. Existing tests also explicitly expect missing purchases to fail and unknown refunds to be ignored (`:544`, `:676`). **Replace:** “Validate `s3e1` online against disposable PostgreSQL, including fresh, fully pre-applied, and partially pre-applied schemas; compare constraints, indexes, defaults and RLS with the PR DDL. Treat hand-derived DDL as unverified until compared, and update the existing assertions intentionally superseded by the new policies.”

**M2 — club-confirmed statistics**

14. **The existing affiliation seam is real; do not leave builders to infer its statuses.** `src/models/showcase.py:399` defines `PlayerClubAffiliation`. Creation is owner-gated at `src/routes/showcase.py:2502`; admin approval produces `self_reported` at `:4810`, while official confirmation produces `club_confirmed` at `:2396`. There is no `approved` affiliation status. `ClubProgramClaim` at `src/models/funding.py:276` links a manager to a program, not a player. **Replace item 1(b):** “Reuse owner-submitted `PlayerClubAffiliation` rows with explicitly accepted moderated statuses (`self_reported` and/or `club_confirmed`); exclude pending/rejected rows and never treat a `ClubProgramClaim` alone as player authority. Test both affiliation approval paths.”

15. **Parent club IDs occupy a different namespace, and players have multiple parent rows.** `TrackedPlayer.team_id` at `src/models/tracked_player.py:28` references `Team.id`; `ClubProgram.team_api_id` at `src/models/funding.py:193` is a provider ID. `_tracked_player` at `src/routes/club.py:446` selects only one row. A fixture where DB and provider IDs accidentally match hides both errors. **Add:** “Resolve parent academy identity through `TrackedPlayer.team_id → Team.id → Team.team_id`, and evaluate all eligible tracked rows rather than `_tracked_player(...).first()`. Test deliberately different DB/provider IDs and a matching academy present only on a second tracked row.”

16. **The authority rule has no time semantics.** `src/models/tracked_player.py:43` holds the current club, while affiliations carry a season at `src/models/showcase.py:417`. Applying today’s authority during every historical rebuild can erase legitimate old-club results after a transfer; accepting any historical academy indefinitely can authorize unrelated future results. Static X/Y tests expose neither. **Replace:** “Define whether authority is for the match date/season or permanently established at entry time, and use that rule consistently on writes and rebuilds; test transfer-away, historical result correction, and an affiliation for a different season. Do not treat current-club equality as an unspecified historical authorization policy.”

17. **Validation in the lineup write loop is too late and covers too few rows.** `src/routes/club.py:1041` mutates every existing fixture row, including players omitted from the incoming lineup, before `:1049` writes requested entries. “No new rows” can pass while an existing unauthorized row is changed. **Replace:** “Validate authority before any fixture/header mutation, covering every player whose existing or new row the request will modify; on rejection roll back the whole transaction. Test unchanged existing entries and rollups, including an unauthorized player omitted from the submitted lineup.”

18. **The rollup guard cannot be optional, and adding it does not repair stored totals.** `_reported_match_cells` at `src/services/season_rollup_service.py:680` is the appropriate feeder seam. `refresh_player` at `:916` rebuilds materialized cells/totals; reads at `src/routes/players.py:919` consume those stored totals. Testing after a rejected insert merely proves that no row was inserted. **Replace:** “Make filtering existing unauthorized club contributions mandatory; seed an unauthorized legacy entry and materialized rollup before testing. Supply an operator handoff to rebuild affected player/season pairs through `refresh_player`, and verify persisted totals as well as feeder output; remove the 30-line escape clause.”

19. **Public match history bypasses the rollup entirely.** `src/routes/player_matches.py:306` selects raw `PlayerMatchEntry` rows for the public listing. Filtering rollup cells leaves legacy misleading `club_confirmed` matches visible there. That route is outside the file fence. **Add:** “Extend the fence to the public match-list authorization/filtering seam, or provide an explicitly approved legacy-row remediation that prevents unauthorized entries appearing there; test the public list and its pagination total in addition to season totals.”

20. **The shared helper must work outside a request and preserve local-player behavior.** `refresh_player(..., session=...)` at `src/services/season_rollup_service.py:916` participates in its caller’s transaction. The local result gate at `src/routes/club.py:611` allows another authorized manager of the same program to operate on an existing local roster member; it does not require the current reporter to be the creator. `club_registry.py:24` also deliberately introspects using the session connection. **Add:** “Place authority logic in a request-independent service accepting the caller’s session; do not import route handlers, read `g`, or commit inside it. Preserve creator authorization at local roster attachment and existing same-program result access, with tests for a second manager and requestless rollup rebuilds.”

21. **The test/file fence names the wrong existing suite and an incorrect POST status.** Result regressions are in `tests/test_club_console.py:653`, not `test_club_results*.py`; its programs currently lack provider identity (`:90`). Roster creation returns **201** at `src/routes/club.py:870`, while GET returns 200. `_member_dict` at `:503` is the common serializer, including unavailable subjects. **Replace:** “Permit and run `test_club_console.py` and affected rollup suites, updating authorized fixtures without weakening their assertions; expect roster POST 201 and GET 200.
